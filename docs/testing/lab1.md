# Лабораторная работа № 1. Unit-тестирование

## 1. Цель и границы работы

В работе тестируются два публичных метода бизнес-логики:

- `CabinetService.AddItem`;
- `MedicineService.Select`.

Подготовлено ровно 10 верхнеуровневых тестов: 5 в классическом стиле и 5 в лондонском. Один и тот же набор сценариев реализован в обоих стилях, чтобы сравнить организацию тестов. Приватные методы `MedicineService` напрямую не вызываются: их поведение проверяется через публичный метод `Select`.

В классических тестах задействованы настоящие реализации трёх PostgreSQL-репозиториев:

- репозиторий пользователя;
- репозиторий лекарства;
- репозиторий аптечки.

Объём тестов зафиксирован договорённостью по лабораторной. Остальные публичные методы сервисов в эту работу не входят.

## 2. Классический и лондонский стили

### Классический стиль

Классический, или sociable, тест проверяет совместную работу нескольких настоящих объектов. В этой работе сервис вызывает настоящую PostgreSQL-реализацию репозитория. Подменяется только внешний SQL-драйвер с помощью `go-sqlmock`, поэтому отдельный сервер PostgreSQL не требуется.

Например, в сценарии обновления позиции аптечки цепочка выглядит так:

```text
CabinetService.AddItem
    -> PostgresCabinetItemRepository.FindExistingCabinetItem
    -> SQL-ожидание SelectExistingByKey
    -> PostgresCabinetItemRepository.Update
    -> SQL-ожидание UpdateQuantity
```

Такой тест обнаруживает не только ошибку в сервисе, но и расхождение между сервисом, SQL-запросом, преобразованием строк БД и репозиторием.

Ограничение подхода: это не полноценный интеграционный тест с настоящей PostgreSQL. Если трактовать требование «без mock / stub» буквально для всей инфраструктуры, понадобилась бы реальная тестовая БД. В работе принят локальный offline-вариант: репозиторий настоящий, а граница с внешней БД заменена `sqlmock`.

### Лондонский стиль

Лондонский, или mockist, тест изолирует сервис от его зависимостей. Вместо репозиториев используются реализации на основе `testify/mock`.

Вызов `repo.On(...)` задаёт ожидаемое взаимодействие и возвращаемое значение. Внутри mock-метода `Called(...)` библиотека находит подходящее ожидание, регистрирует фактический вызов и возвращает настроенные значения. `Once()` требует ровно один вызов, `AssertExpectations` проверяет все ожидания, а `AssertNotCalled` подтверждает отсутствие лишнего обращения.

Лондонский тест лучше локализует ошибку бизнес-логики и позволяет точно проверить протокол взаимодействия. Его недостаток — более сильная связь теста со способом реализации сервиса.

## 3. Использованные техники тест-дизайна

Стиль тестирования и техника тест-дизайна отвечают на разные вопросы:

- стиль определяет, настоящие зависимости или mock-объекты участвуют в тесте;
- техника определяет, какие входные данные и сценарии выбраны.

В работе используются:

- **Переход состояния** — количество существующей позиции изменяется с 5 до 8.
- **Классы эквивалентности** — отдельно рассматриваются найденная и отсутствующая позиции аптечки.
- **Граничные значения** — проверяется `quantity = 0` и вес пользователя `70`, равный нижней границе диапазона дозировки `[70, 90]`.
- **Таблица решений** — результат выбора лекарства зависит от безопасности для пользователя, наличия, срока годности и положительного остатка.
- **Комбинаторная выборка** — вместо полного перебора отдельно представлены допустимое лекарство и причины исключения: ограничения пользователя, отсутствие в аптечке, истёкший срок годности и совокупность отрицательных условий.
- **Внедрение ошибки** — репозиторий лекарства возвращает ошибку SQL, после чего сервис должен вернуть `ErrInternal` и не обращаться к аптечке.

## 5. Подготовка тестовых данных

### Data Builder

В `src/internal/test_util/builders.go` находятся `UserBuilder`, `MedicineBuilder` и `CabinetItemBuilder`. Конструктор задаёт корректный объект по умолчанию, методы `With...` изменяют только нужные поля, а `Build()` возвращает готовый объект предметной области, а не builder.

Коллекции при `Build()` копируются. Поэтому последующее изменение builder не должно незаметно изменить уже созданный объект.

### Object Mother

В `src/internal/test_util/mother.go` находятся именованные типовые объекты:

- `TestUser`;
- `SafeMedicine`;
- `AvailableCabinetItem`.

Object Mother описывает смысловой образ объекта, а Builder позволяет точечно изменить его поля.

### Fixtures и helpers

Fixture `NewMedicineSelection` собирает согласованный граф объектов: пользователя, заболевание, аллерген, лекарства и содержимое аптечки. В набор входят безопасное, опасные при беременности и вождении, противопоказанное, аллергенное, отсутствующее, просроченное лекарство и комбинация отрицательных условий.

SQL-fixtures создают строки `sqlmock.Rows`, соответствующие структурам настоящих PostgreSQL-репозиториев. Helpers `Expect...` задают ожидаемый SQL-запрос, аргументы и результат. `ClassicRepositories` создаёт отдельное соединение `sqlmock` и настоящие реализации трёх репозиториев для каждого теста; соединение закрывается через `t.Cleanup`.

## 6. Запуск из командной строки

Все команды выполняются из корня `dev`.

```bash
# Пять классических тестов
make test-classic

# Пять лондонских тестов
make test-london

# Все 10 тестов, Allure results и statement coverage
make test

# Все 10 тестов без получения зависимостей из сети
make test-offline

# Сформировать или открыть Allure-отчёт
make allure-report
make allure-open

# Установить gocove и сформировать branch/condition coverage
make install-gocove
make coverage-branch

# Удалить только тестовые либо все генерируемые артефакты
make test-clean
make clean
```

`make test-offline` задаёт `GOPROXY=off`. Перед первым offline-запуском Go-зависимости должны уже находиться в локальном module cache. PostgreSQL, MongoDB, SMTP и другие внешние сервисы для тестов не требуются.

Allure CLI запускается через `npx` только при генерации или открытии HTML-отчёта. Сами тесты записывают JSON-результаты через Go-адаптер в корневой каталог `allure-results`.

## 7. Порядок тестов и процессы

В тестовых целях используются параметры:

- `-shuffle=on` случайно меняет порядок тестов и печатает seed, с которым порядок можно воспроизвести;
- `-count=1` отключает использование сохранённого результата успешного теста;
- `-run '^TestClassic_'` и `-run '^TestLondon_'` выбирают стиль тестов.

Цели передают `go test` один пакет — `./src/internal/service`. Go собирает для каждого указанного пакета отдельный test binary, поэтому в данном прогоне выполняется один тестовый бинарник. Ни один тест не вызывает `t.Parallel`, следовательно, верхнеуровневые тесты внутри него выполняются последовательно. Параметр `-parallel` влияет только на тесты, явно вызвавшие `t.Parallel`, а параметр сборки `-p` управляет параллельным тестированием разных пакетов.

Количество тестовых процессов проверено фактически командой:

```bash
go test -x -count=1 -shuffle=on ./src/internal/service
```

В трассировке присутствовал ровно один запуск тестового бинарника:

```text
$WORK/b001/service.test -test.paniconexit0 -test.timeout=10m0s -test.count=1 -test.shuffle=on
```

Дополнительная проверка `go test -x -count=1 ./...` также показала только один тестовый бинарник `service.test`, поскольку в остальных пакетах проекта файлов `*_test.go` нет.

Итоговая модель выполнения:

- команда `go test` является управляющим процессом и во время сборки может запускать служебные процессы компилятора, vet и linker;
- непосредственно все 10 unit-тестов выполняет один процесс `service.test`;
- отдельный процесс для каждого файла, условного test class или отдельного теста не создаётся;
- в стандартном Go нет test class: все `*_test.go` одного пакета компилируются в общий тестовый бинарник;
- `allure.Wrap` не создаёт дополнительный `t.Run` и не меняет количество процессов;
- список пакетов в команде определяет количество тестовых бинарников, `-p` ограничивает параллельную обработку пакетов, а `t.Parallel` вместе с `-parallel` управляет параллельностью тестов внутри одного бинарника;
- `GOMAXPROCS` управляет количеством потоков выполнения Go runtime, а не количеством тестовых процессов.

## 8. Allure

Каждый верхнеуровневый Go-тест обёрнут в `allure.Wrap`. В отличие от `allure.Test`, этот вариант не создаёт дополнительный `t.Run`, поэтому результатам Allure соответствуют ровно 10 верхнеуровневых тестов.

Для каждого результата записываются:

- метка `style`: `classic` или `london`;
- метка `technique`;
- метка `service`;
- шаги `Arrange`, `Act`, `Assert`.

Проверенный отчёт содержал 10 тестов: 10 passed, 0 failed.

## 9. Покрытие

### Стандартное покрытие Go

`make test` запускает:

```bash
go test -covermode=count -coverprofile=coverage.out ./src/internal/service
go tool cover -func=coverage.out
```

Go сообщает **statement coverage**, то есть долю выполненных операторов, а не буквальную долю строк файла. Профиль при этом содержит диапазоны строк исходного кода и может быть представлен в HTML.

Последний зафиксированный результат для всего пакета `service`:

```text
statements: 18.1%
```

В знаменатель входят также остальные production-файлы пакета `service`, которые не относятся к выбранным двум методам. Поэтому общий процент заметно ниже покрытия непосредственно `AddItem` и `Select`.

### Ветви, блоки и условия

Стандартный инструмент Go не выводит branch/condition coverage. Цель `make coverage-branch` использует `gocove`, который дополнительно инструментирует условия и формирует текстовый, JSON- и HTML-отчёты.

Последний фактический вывод `gocove`:

```text
conditions: 74
conditions hit: 14
conditions fully covered: 6
condition coverage: 8.1%
block coverage: 13.9%
branch coverage: 10.0%
```

Значения означают:

- **condition coverage 8.1%** — для 6 из 74 логических условий наблюдались оба результата, `true` и `false`;
- **block coverage 13.9%** — такая доля структурных блоков production-кода была выполнена;
- **branch coverage 10.0%** — такая доля точек ветвления прошла все учитываемые инструментом ветви.

Это показатели всего пакета `service`, а не только двух тестируемых методов. Порог покрытия заданием не установлен, поэтому искусственные exclusions и неподтверждённый Quality Gate не применяются.
