# WebLab №5 — база и экземпляры API

Это первый этап WebLab №5. Дополнительный Compose-файл сохраняет существующий
том `pgdata` как primary, создаёт отдельный том `lab5_replica_data` для потоковой
реплики и запускает шесть экземпляров Go API. Основной и зеркальный экземпляры
с правом записи подключаются к primary. Два читателя основной версии подключаются
к primary под ролью `lab5_reader`; два читателя зеркальной версии — к replica под
той же ролью. Внутренние порты экземпляров: `8081`–`8086`.

## Запуск

В `.env` должны быть заполнены `DB_PASSWORD`, `SECRET_KEY`,
`LAB5_READ_PASSWORD`, `LAB5_REPLICATION_PASSWORD` и `LAB5_MONITOR_PASSWORD`.
Для трёх паролей WebLab №5 подойдут независимые результаты `openssl rand -hex 32`. Локальный `.env` не
добавляется в Git.

```sh
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml up -d --build
```

Подготовка ролей выполняется контейнером `db-bootstrap` после готовности primary.
Она повторяемая и работает с уже существующим томом БД. Реплика создаётся из
primary только при пустом собственном томе; при повторном запуске использует
уже полученные данные. Не применяйте `down -v` к стенду с нужными данными.

## Проверка

Во всех командах ниже можно добавить `-p <имя-проекта>` сразу после
`docker compose`, если стенд запущен с отдельным именем проекта.

```sh
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml config --quiet
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml ps -a
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml exec -T db \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atqc "SELECT state FROM pg_stat_replication"'
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml exec -T db-replica \
  sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -h 127.0.0.1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atqc "SELECT pg_is_in_recovery()"'
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml exec -T db \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atqc "SELECT has_table_privilege('\''lab5_reader'\'', '\''users'\'', '\''SELECT'\''), has_table_privilege('\''lab5_reader'\'', '\''users'\'', '\''UPDATE'\'')"'
```

Ожидается: `db-bootstrap` завершён с кодом `0`, обе БД здоровы, шесть API
экземпляров здоровы, состояние репликации — `streaming`, на replica запрос
`pg_is_in_recovery()` возвращает `t`, а проверка прав — `t|f`.

## Демонстрация одной командой

На запущенном стенде выполните из каталога `dev`:

```sh
make check-web5
```

Демо занимает около 35–40 секунд и выводит четыре коротких блока.

1. Прямой POST к каждому из четырёх читателей с настоящим HTTP 503 и JSON
   ошибки `READ_ONLY_INSTANCE`.
2. Счётчики 40 чтений для обычного входа и зеркала. Ожидается примерно
   20 / 10 / 10 ответов.
3. Заголовок gzip и размер HTML до и после сжатия для обеих версий интерфейса.
4. Создание тестовой аптечки через зеркало. С cookie восемь чтений идут на
   primary (8084). После реального ожидания 30 секунд 40 чтений снова
   распределяются между 8084, 8085 и 8086, а читатели реплики видят запись.
   Демо читает содержимое пустой аптечки через оба входа, чтобы в Grafana
   появились измерения и для фильтра «Содержимое аптечки». Prometheus собирает
   данные раз в 5 секунд, поэтому после демо дождитесь обновления панели.

Каждый блок проверяет фактический ответ. При ошибке команда завершится
с ненулевым кодом. Временные пользователь и аптечка удаляются в конце,
в том числе при ошибке проверки. Записи запросов остаются в метриках и логах.
Для наглядного распределения запускайте демо без параллельной нагрузки.

Для другого адреса и Compose-проекта передайте оба параметра:

```sh
make check-web5 WEB5_BASE_URL=http://127.0.0.1:18085 WEB5_PROJECT=mypills-lab5-check
```

## Режим только для чтения

Перед запуском API контейнер `db-bootstrap` переносит старые позиции без
`cabinet_id` в «Домашнюю аптечку» их владельцев. Идентификаторы и количество
позиций сохраняются. Перенос выполняется целиком в одной транзакции на primary.
Повторный запуск пропускает уже перенесённые позиции. Если используется старый том
со стендом без WebLab №5, тот же SQL можно выполнить вручную перед обновлением API:

```sh
docker compose exec -T db sh -ec 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < lab5/migrate-legacy-cabinets.sql
```

GET-запросы к спискам аптечек, их содержимому и рекомендациям только читают
данные. При добавлении новой позиции через API v1 сервер сразу связывает её с
домашней аптечкой. Четыре читателя используют `APP_MODE=read_only` и блокируют
запросы с методами записи на уровне HTTP. Права PostgreSQL остаются второй
проверкой.

После запуска стенда выполните команду из каталога `dev`:

```sh
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml exec -T app-read-1 \
  sh -c 'wget -qO- "http://127.0.0.1:$SERVER_PORT/api/v2/reference" &&
         wget -S -O /dev/null --post-data="{}" "http://127.0.0.1:$SERVER_PORT/api/v2/users"'
```

GET вернёт JSON со ссылками на справочники. На POST ожидается HTTP 503, поэтому
`wget` завершится с ошибкой. Код в теле HTTP-ответа — `READ_ONLY_INSTANCE`.
Тот же результат ожидается у `app-read-2`, `mirror-read-1` и `mirror-read-2`.

## Балансировка API

Nginx направляет GET и HEAD к трём экземплярам с весами `2:1:1`.
Для `/api/v1/` и `/api/v2/` это `app`, `app-read-1` и `app-read-2`.
Для `/mirror/api/v1/` и `/mirror/api/v2/` используется своя тройка
`mirror-app`, `mirror-read-1` и `mirror-read-2`. Остальные методы идут
к единственному экземпляру с правом записи из соответствующей группы.

При сбое экземпляра Nginx может повторить чтение на другом экземпляре
той же группы. Если единственный писатель недоступен, запрос на запись
завершается ошибкой шлюза.

Чтобы увидеть фактическое распределение, выполните из каталога `dev`:

```sh
for i in $(seq 1 40); do
  curl -fsS -o /dev/null -D - http://127.0.0.1:8088/api/v2/reference
done | awk 'tolower($1) == "x-upstream-addr:" {print $2}' | sort | uniq -c
```

На стенде без параллельного трафика ожидается примерно 20 ответов от
писателя и по 10 от читателей. Для проверки зеркальной тройки замените путь
на `/mirror/api/v2/reference`. Заголовок `X-Upstream-Addr` содержит адрес и
порт фактического экземпляра. Если Nginx повторил запрос, он перечисляет
адреса всех попыток. В журнале Nginx есть те же адреса, HTTP-метод, пул и
статус каждой попытки:

```sh
docker compose -f docker-compose.yaml -f docker-compose.lab5.yaml logs --tail=20 nginx
```

Остановку экземпляров для проверки отказа выполняйте на отдельном
Compose-проекте и томе, например с `-p mypills-lab5-check` и
`WEB_PORT=18085`. После остановки читателя чтение должно продолжать работать.
После остановки писателя чтение также доступно, а запросы записи возвращают
ошибку шлюза.


## Зеркальный интерфейс

Обычный вход остаётся по адресу `http://127.0.0.1:8088/`. Откройте
`http://127.0.0.1:8088/mirror/` и нажмите «Открыть приложение», чтобы перейти
к отдельной сборке GUI по `/mirror/legacy/`. У обеих версий одна база учётных
записей, а сеансы входа в браузере хранятся отдельно.

- Зеркальный GUI обращается к `/mirror/api/v2/`.
- Swagger для зеркала доступен по `/mirror/api/v1/docs/` и `/mirror/api/v2/docs/`.
  Выполненные из Swagger запросы тоже идут через зеркальный API.
- Документация зеркала доступна по `/mirror/documentation`. Её ссылки и
  изображения, а также API-ссылки и заголовок `Location` после создания объекта
  сохраняют префикс `/mirror`.

Чтобы проверить чтение после записи, откройте вкладку Network в инструментах
разработчика браузера. Войдите через зеркало и добавьте аптечку. Успешный POST
установит cookie `mypills_mirror_primary` на 30 секунд. Следующие GET-запросы
этого браузера к зеркальному API пойдут в `mirror-app:8084`, который читает из
основной БД. Порт виден в заголовке `X-Upstream-Addr`. По окончании 30 секунд
запросы снова распределяются между портами 8084, 8085 и 8086. Клиенты без
cookie распределяются сразу и при отставании реплики могут увидеть прежнее
состояние.

На отдельном стенде проверили эту разницу с приостановленным применением WAL
на реплике. Клиент с cookie сразу увидел созданную аптечку. Без cookie оба
читателя реплики показывали прежнее состояние. После возобновления применения
WAL они увидели запись примерно через 0,05 с в одном тестовом прогоне. После
истечения cookie 40 чтений распределились между экземплярами как 20 / 10 / 10.

## Заголовки, кэш и мониторинг

WebLab №5 использует OpenResty с модулем Headers More и публикует
`Server: MyPills`. Браузер кэширует сборки JS и CSS с хешем в имени на год,
а публичные PNG из `/static/img/` и `/mirror/static/img/` — на час.
HTML, API, персональные ответы и служебные маршруты используют
`Cache-Control: no-store`. Текстовые ответы подходящего размера сжимаются gzip
по запросу клиента.

```sh
curl -sSI http://127.0.0.1:8088/static/img/img1.png
curl -sS -D - -o /dev/null http://127.0.0.1:8088/api/v2/reference
curl -sS -D - -o /dev/null -H 'Accept-Encoding: gzip' http://127.0.0.1:8088/mirror/legacy/
```

Откройте [панель Grafana](http://127.0.0.1:8088/monitoring/). Prometheus
собирает метрики HTTP и пула соединений со всех шести экземпляров API и
статистику обеих БД. Alloy отправляет журналы API и Nginx в Loki. На панели
видны доступность, интенсивность, p95 чтения, доля ответов 5xx, распределение
чтений и ожидание соединений. Переключатель «Чтения» выбирает все успешные GET API или только чтение содержимого
аптечки. Для эксперимента выберите «Содержимое аптечки». Доли чтений считаются за
весь выбранный период, а p95 — за короткое окно. Без таких запросов p95 не
определён, поэтому панель показывает «Нет запросов». Нулевое ожидание соединений
означает отсутствие ожиданий. Запросы демо на читатели с ожидаемым HTTP 503
попадают в долю 5xx.

Для просмотра конкретного экземпляра в Explore
выберите Loki и запросите `{job="mypills-api",backend="mirror-read-1"}`.
`/metrics`, Prometheus, Loki и экспортеры доступны во внутренней сети Compose.
Веб-вход Grafana доступен через Nginx с локального адреса в режиме просмотра.

## Нагрузочный эксперимент

Гипотеза перед запуском — при лимите 6 соединений на экземпляр часть запросов
может ждать соединение с БД. Лимит 12 имеет смысл сохранять, если ожидание
действительно было и уменьшилось вместе с p95 без роста ошибок. Если оба
прогона проходят критерии и разница укладывается в разброс замеров, оставить 6.

На одном компьютере запустите варианты последовательно при одинаковой фоновой
нагрузке. Скрипт создаёт для каждого прогона отдельный Compose-проект с пустыми
БД и одинаковыми тестовыми данными. Между вариантами меняется только
`DB_MAX_OPEN_CONNS` с 6 до 12, а лимит простаивающих соединений остаётся равным
6. Основной стенд на 8088 может работать во время обоих прогонов, если до
окончания сравнения на него не подаётся дополнительная нагрузка. Порт для
эксперимента по умолчанию 18085.

```sh
sh scripts/bench-web5.sh 6
sh scripts/bench-web5.sh 12
```

k6 делает 30 секунд прогрева и 180 секунд измерения при 20 запросах/с.
Из них 16 чтений содержимого аптечки и 4 записи количества в отдельные
позиции. Половина каждого типа запросов идёт через зеркало. Каждый запрос
использует отдельную итерацию. Cookie закрепления не переносится между ними,
поэтому измеряется обычное распределение чтений. Подготовка данных и прогрев
не входят в итоговую таблицу. Критерии — p95 чтения до 1 с на обоих входах,
меньше 1% ошибок, без пропущенных итераций и с распределением чтений около
2:1:1 внутри каждой группы с отклонением не более 5 процентных пунктов.

В `benchmark-results/` сохраняются сырые точки k6, итоговая таблица,
консольный вывод, конфигурация окружения и снимок счётчиков пула. Скрипт
останавливает тестовый стенд после прогона и сохраняет его тома. При необходимости
откройте Grafana тестового проекта и сверьте интервал с временными метками k6.
После двух прогонов сравните p95, достигнутую интенсивность, ошибки, выбранные
узлы и счётчики ожидания, затем внесите фактические результаты в отчёт.
