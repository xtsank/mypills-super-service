# WebLab №5 — MyPills

## Результат

Реализованы две версии приложения по `/` и `/mirror/`, по три экземпляра
Go API для каждой версии, потоковая реплика PostgreSQL, разделение чтения
и записи, кэш публичных файлов, gzip и наблюдаемость через `/monitoring/`.
Стенд запускается совместным применением `docker-compose.yaml` и
`docker-compose.lab5.yaml`. Бонусные задания в эту работу не входят.

[Запуск и проверка стенда](lab5-infrastructure.md).
[Демо разделения серверов](lab5-infrastructure.md#демонстрация-одной-командой).

## Конфигурация и защита данных

| Вход | Экземпляр | Порт | Роль | Подключение |
|---|---|---:|---|---|
| `/` | app | APP_PORT, по умолчанию 8081 | Чтение и запись | Primary |
| `/` | app-read-1 | 8082 | Только чтение | Primary |
| `/` | app-read-2 | 8083 | Только чтение | Primary |
| `/mirror/` | mirror-app | 8084 | Чтение и запись | Primary |
| `/mirror/` | mirror-read-1 | 8085 | Только чтение | Replica |
| `/mirror/` | mirror-read-2 | 8086 | Только чтение | Replica |

В каждой группе GET и HEAD распределяются с весами 2:1:1. Методы записи идут
на единственный экземпляр с правом записи соответствующей группы.
`X-Upstream-Addr` и журнал Nginx позволяют проверить фактический узел.
Ошибки соединения и подходящие ошибки upstream допускают повтор чтения.
Группа записи содержит только своего писателя.

Роль `lab5_reader` имеет SELECT и не имеет UPDATE на таблицы приложения.
Четыре читателя запускаются с `APP_MODE=read_only`. Прямой POST возвращает
HTTP 503 с кодом `READ_ONLY_INSTANCE`. Это проверено на всех четырёх экземплярах.
Дополнительно проверялся отказ PostgreSQL с SQLSTATE 42501 при UPDATE под
ролью читателя даже после отключения флага read-only внутри транзакции.

Старые позиции без аптечки переносятся перед запуском API в одной транзакции.
GET-сценарии больше не выполняют этот перенос. Запись позиции через v1 сразу
привязывает её к домашней аптечке владельца.

Primary сохраняет существующий том, replica имеет свой том и получает WAL.
Подготовка ролей и слота репликации повторяема. Репликация асинхронная.
Зеркальный интерфейс, Swagger, API-ссылки и Location сохраняют префикс
`/mirror`. После успешной записи браузер получает cookie на 30 секунд.
В этот период чтения зеркального API направляются на mirror-app с primary.
После истечения cookie возвращается обычная балансировка. Клиенты без cookie
могут увидеть прежнее состояние при отставании реплики.

На отдельном стенде приостанавливали применение WAL. Клиент с cookie сразу
увидел новую аптечку, читатели реплики показывали прежнее состояние.
После возобновления применения WAL оба читателя получили запись примерно
через 0,05 с в одном проверочном прогоне. Это наблюдение одного локального теста,
а не гарантия задержки репликации.

## Кэширование и наблюдаемость

OpenResty с Headers More устанавливает `Server: MyPills`.
Публичные JS/CSS с хешем в имени получают
`Cache-Control: public, max-age=31536000, immutable`, изображения PNG — час.
HTML, API и служебные страницы получают `no-store`. Подходящие текстовые
ответы сжимаются gzip. Проверены обе версии GUI и ответы API, /admin,
/management, /status, /health, /ready, а также отсутствующие файлы.

Prometheus каждые 5 секунд получает HTTP-гистограммы и статистику пула со всех
шести API, а через экспортеры — статистику primary и replica. Alloy собирает
семь потоков журналов API и Nginx в Loki. Grafana показывает доступность,
интенсивность, p95, долю 5xx, распределение чтений и ожидание соединений.
Поступление метрик и журналов от всех экземпляров проверено через источники
Grafana. Панель доступна по `/monitoring/` с ролью Viewer на локальном входе.
Порты хранилищ мониторинга и /metrics остаются внутри Compose.

## Гипотеза и план эксперимента

До запуска сформулирована гипотеза, что при максимуме 6 открытых соединений
на экземпляр запросам придётся ждать освобождения соединения, а повышение
лимита до 12 уменьшит ожидание и p95. Проверяемое изменение — максимум
открытых соединений. Максимум простаивающих соединений равен 6 в обоих вариантах.

Использованы два последовательных прогона 23 ноября 2026 года на одном
компьютере. Docker сообщил 12 CPU и 15 366 344 704 байта памяти. Точные
версионные образы и их ID сохранены в environment.txt каждого прогона.

| Условие | Значение |
|---|---|
| Генератор | k6 1.6.1 |
| Прогрев | 30 с |
| Измерение | 180 с |
| Целевой темп | 20 запросов/с суммарно |
| Чтения | 16 GET содержимого аптечки/с |
| Записи | 4 PATCH количества/с |
| Входы | Половина чтений и записей через каждый вход |
| Данные | Новый пользователь, две аптечки, по 20 позиций |
| Изоляция | Отдельный Compose-проект и пустые тома для каждого прогона |

Чтения и записи используют отдельные аптечки. Данные реплики проверяются
до начала нагрузки. Cookie не переносится между итерациями, поэтому
измеряется обычное распределение чтений. Подготовка и прогрев исключены
из итоговой таблицы. Критерии приёмки определены до теста — p95 до 1000 мс,
менее 1% ошибок, отсутствие пропущенных итераций, доли чтений около 50/25/25
с допуском 5 процентных пунктов.

```sh
sh scripts/bench-web5.sh 6
sh scripts/bench-web5.sh 12
```

Идентификаторы полных прогонов:

- `mypills-lab5-exp-6-1795434662`, начало по environment.txt — 14:51:46 МСК.
- `mypills-lab5-exp-12-1795434975`, начало — 14:56:42 МСК.

## Измерения

| Лимит | Вход | GET | PATCH | Запросов/с | Ошибки | p95 GET, мс | Чтения по портам |
|---|---|---:|---:|---:|---:|---:|---|
| 6 | / | 1440 | 361 | 10,01 | 0 | 2,61 | 8081 → 720, 8082 → 360, 8083 → 360 |
| 6 | /mirror | 1440 | 360 | 10,00 | 0 | 2,77 | 8084 → 720, 8085 → 360, 8086 → 360 |
| 12 | / | 1441 | 361 | 10,01 | 0 | 2,47 | 8081 → 720, 8082 → 360, 8083 → 361 |
| 12 | /mirror | 1440 | 360 | 10,00 | 0 | 2,60 | 8084 → 720, 8085 → 360, 8086 → 360 |

Измерено 3601 и 3602 операции за 180 с соответственно, то есть примерно
20 запросов/с. Незначительное отличие числа операций связано с границами
итераций генератора. Пропущенных итераций в обоих прогонах нет.
Лимиты 6 и 12 подтверждены метрикой go_sql_max_open_connections всех шести
API. У всех экземпляров в обоих снимках go_sql_wait_count_total и
go_sql_wait_duration_seconds_total равны нулю.

При увеличении лимита p95 уменьшился с 2,6105 до 2,4708 мс для обычного
входа и с 2,7669 до 2,5980 мс для зеркала. Разница составляет около
0,14–0,17 мс. Выполнен один прогон каждого варианта, поэтому оценить
естественный разброс и приписать это изменение настройке пула нельзя.
Ожиданий соединений не было даже при лимите 6.

**Вывод.** При 20 запросах/с гипотеза о нехватке соединений не подтвердилась.
Оба варианта удовлетворяют критериям, балансировка работает.
Для WebLab №5 выбран лимит 6 на экземпляр и максимум 6 простаивающих
соединений. Они заданы через LAB5_DB_MAX_OPEN_CONNS и LAB5_DB_MAX_IDLE_CONNS,
чтобы настройки старого стенда в .env не переопределяли результат выбора.

## Проверка отказа и восстановления

Следующие сценарии выполнялись на отдельном тестовом стенде при реализации
балансировки. Эти наблюдения относятся к функциональной проверке маршрутизации,
а нагрузочные результаты выше относятся к двум сохранённым полным прогонам.

| Сценарий | Наблюдение |
|---|---|
| Остановлен первый читатель каждой группы | По 40 GET через оба входа вернули 200. Ответы распределились между оставшимися узлами как 27/13. Запросы записи продолжили идти писателю. |
| Читатели запущены снова | В каждой группе 80 GET распределились 40/20/20. |
| Остановлены app и mirror-app | По 40 GET каждого входа вернули 200, по 20 на каждого читателя. Запросы записи получили ошибку шлюза. Перенаправления записи на читателей не было. |
| Писатели запущены снова | Обе группы снова показали 40/20/20 и правильное направление записи. |

Обнаружение отказа основано на неуспешных запросах Nginx с max_fails=1 и
fail_timeout=5s. После восстановления узел снова принимает запросы.
Активные HTTP-проверки upstream относятся к бонусу и здесь не реализованы.

## Исходные данные и воспроизводимость

[Архив прогона с лимитом 6](lab5-results/pool-6/summary.md).
[Архив прогона с лимитом 12](lab5-results/pool-12/summary.md).

Из публикуемых k6-summary.json удалён setup_data.token, содержащий сеанс
тестового пользователя. Числовые метрики сохранены полностью. Скрипт новых
прогонов выполняет такую же очистку автоматически.

В каждом каталоге сохранены samples.jsonl.gz, k6-summary.json, k6-output.txt,
environment.txt, db-pool.json и SHA256SUMS. Сжатые точки побайтно совпадают
с исходными JSONL после распаковки. Их можно проверить и повторно собрать
таблицу без запуска контейнеров:

```sh
(cd docs/web/lab5-results/pool-6 && sha256sum -c SHA256SUMS)
(cd docs/web/lab5-results/pool-12 && sha256sum -c SHA256SUMS)
gzip -dc docs/web/lab5-results/pool-6/samples.jsonl.gz > /tmp/web5-pool-6.jsonl
python3 scripts/summarize-web5.py /tmp/web5-pool-6.jsonl 180
```

В k6-summary.json значение false в thresholds означает отсутствие нарушения
порога. В k6-output.txt те же проверки отмечены галочками. Итоговые проценты
ошибок проверялись по value и исходным точкам, а не по названиям passes/fails
у пользовательской метрики Rate.

Ограничения измерений — локальный компьютер, небольшой учебный набор данных,
один прогон каждого варианта и фиксированный темп 20 запросов/с. Результат
не определяет максимальную пропускную способность. Образы пересобирались
перед каждым прогоном и имеют разные ID, зафиксированные в environment.txt.
Побайтовое равенство бинарников архивами результатов не подтверждается.
Снимки ожиданий накопительные с запуска API и включают подготовку и прогрев.
В данном случае все значения равны нулю и за весь этот интервал.

docker compose config --quiet

go vet ./..., сборка GUI, 61 HTTP-проверка make check-web4 и make check-web5.

прямой POST на читатели, балансировку обеих групп, gzip и реальное истечение
cookie зеркала. Обновление документации и результаты работы ИИ отражены в
