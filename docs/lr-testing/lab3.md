# ЛР № 3. SQL и GORM в MyPills

## Изолированный стенд

Команды выполняются из корня репозитория `dev/`. Для стенда нужен Docker с Compose.

```sh
docker compose -p mypills-lab3 -f docker-compose.lab3.yaml up -d --wait db
```

Стенд использует свой Compose-проект и том. PostgreSQL доступен внутри сети
Compose под именем `db`. При создании пустого тома сначала загружается схема
MyPills, затем добавляются 10 000 синтетических лекарств с фиксированными ID.

Посмотреть количество записей и контрольную сумму каталога можно так:

```sh
docker compose -p mypills-lab3 -f docker-compose.lab3.yaml exec -T db \
  psql -U mypills_lab3 -d mypills_lab3 -v ON_ERROR_STOP=1 <<'SQL'
SELECT count(*) AS medicines,
       md5(string_agg(row_to_json(m)::text, E'\n' ORDER BY m.id)) AS fingerprint
FROM Medicine AS m;
SQL
```

Для повторной проверки удалите том **стенда ЛР № 3**, снова запустите стенд и
выполните запрос выше. Число записей должно остаться равным 10 000, а контрольная
сумма должна совпасть.

```sh
docker compose -p mypills-lab3 -f docker-compose.lab3.yaml down -v
docker compose -p mypills-lab3 -f docker-compose.lab3.yaml up -d --wait db
```

## Запуск бенчмарка

```sh
make bench-lab3 PROFILE=smoke
make bench-lab3
```

Короткий режим выполняет один повтор с 5 операциями прогрева и 20 замерами
на каждую выборку. Полный режим выполняет три повтора с 50 операциями прогрева
и 1 000 замерами на выборку. Один запуск собирает отдельный образ раннера и
создаёт временный Docker Compose-проект с PostgreSQL. Раннер и PostgreSQL
закреплены за одним ядром. При необходимости его можно указать явно,
например `LAB3_CPU=2 make bench-lab3`.

Перед замерами раннер проверяет ожидаемые результаты SQL и GORM на копии
исходной базы. Каждая серия также получает отдельную копию исходной базы.
После запуска временные контейнеры и том удаляются.

## Операции

| Сценарий | Операция |
| --- | --- |
| `find` | Прочитать лекарство по ID. |
| `count` | Подсчитать совпадения по подстроке названия без учёта регистра. |
| `page` | Прочитать до 20 совпадений с сортировкой по названию и ID. |
| `insert` | Вставить лекарство с заранее подготовленным ID. |
| `rename` | Изменить название по ID. |
| `delete` | Удалить одну запись по ID. |
| `mixed` | Параллельно читать страницы «Альфа» и обновлять записи за пределами этих страниц через два соединения. |

Обе реализации работают с одинаковыми полями и используют драйвер pgx.
Для записи время операции включает проверку числа затронутых строк и
`COMMIT`. В смешанном сценарии раннер проверяет пересечение интервалов
чтения и записи и сохраняет для них отдельные замеры.

## Результаты

Результаты сохраняются в `benchmark-results/<run-id>/` после завершения
измерений:

- `samples.csv` содержит по одной строке на операцию, включая прогрев,
  абсолютное время начала, смещение от начала серии, длительность в
  наносекундах и статус.
- `summary.json` содержит конфигурацию, число операций и время по фазам,
  состояние серий и перцентили p50, p75, p90, p95 и p99 по успешным
  операциям основной фазы. Перцентили вычисляются методом ближайшего ранга.
- Контрольный цикл даёт медианное время пустой операции и среднее время
  итерации с учётом записи результата в память. Эти значения сохраняются
  отдельно от результатов SQL и GORM.
- При ошибке операции сохраняются уже собранные замеры и причина остановки.
  Фаза завершения содержит время закрытия пула и удаления копии БД, число
  измеряемых операций в ней равно нулю.

## Дашборд Grafana

После прогона возьмите `run-id` из имени папки с результатами и выполните:

```sh
make bench-lab3-report RUN_ID=<run-id>
```

Команда импортирует `samples.csv` и `summary.json` в отдельную PostgreSQL и
печатает ссылку на дашборд. Повторный импорт заменяет данные этого прогона в
одной транзакции. Grafana доступна локально на порту 3003 и читает данные
через учётную запись с правом `SELECT`. Порт можно изменить через
`LAB3_GRAFANA_PORT`.

В верхней части дашборда выберите прогон, сценарий и повтор. Графики и
перцентили используют успешные операции основной фазы. На графике времени
ноль соответствует началу замеров каждого варианта. В `mixed` SQL и GORM
показывают чтение страницы, а серии «запись» — переименование.
Таблица фаз отдельно показывает число операций и длительность прогрева,
измерения и завершения.

Остановить Grafana и базу результатов с сохранением импортированных данных:

```sh
docker compose -p mypills-lab3-report -f docker-compose.lab3-report.yaml down
```

## Выводы по полному прогону

Прогон `20261112t093514z-1226626` выполнен на PostgreSQL 16.13 и Go 1.26.2.
Раннер и PostgreSQL были закреплены за одним ядром CPU 0. За 106,08 с
выполнены 42 серии, собрано 48 000 замеров и выполнено 2 400 операций
прогрева. Все измеренные операции завершились успешно. В каждой из шести
смешанных серий интервалы чтения и записи перекрылись.

В таблице приведены медианы трёх значений каждого перцентиля, рассчитанного
отдельно по каждому повтору. Задержки указаны в миллисекундах.

| Операция | SQL p50 | GORM p50 | SQL p95 | GORM p95 |
| --- | ---: | ---: | ---: | ---: |
| Поиск по ID | 0,099 | 0,110 | 0,118 | 0,138 |
| Подсчёт совпадений | 4,094 | 4,122 | 4,361 | 4,390 |
| Чтение страницы | 4,971 | 5,008 | 5,612 | 5,653 |
| Вставка | 0,390 | 0,408 | 0,435 | 0,448 |
| Переименование | 0,350 | 0,375 | 0,378 | 0,415 |
| Удаление | 0,507 | 0,505 | 0,545 | 0,549 |
| Чтение страницы при записи | 5,043 | 5,104 | 8,697 | 8,736 |
| Переименование при чтении | 0,362 | 0,378 | 2,069 | 2,436 |

- **Поиск по ID показал наибольшую повторяемую разницу по p50.** У GORM
  медиана была на 8,8–12,7% выше, чем у прямого SQL, во всех трёх повторах.
  Для вставки разница составила 3,4–4,7%, для переименования — 4,9–8,6%.
- **Подсчёт, чтение страницы и удаление дали близкие медианы.** Для подсчёта
  и удаления преимущество по p50 переходило от одного варианта к другому.
  При чтении страницы p50 у GORM был выше на 0,6–3,8%, а направление
  разницы по p95 менялось между повторами.
- **Одновременное чтение и запись сильнее повлияли на хвост задержек.**
  При переходе к смешанному сценарию p50 переименования изменился менее чем
  на 5% в каждом повторе, а медианный p95 вырос примерно в 5,5 раза для
  прямого SQL и в 5,9 раза для GORM. Для чтения страницы медианный p95
  вырос примерно на 55% у обоих вариантов. При этом GORM в одном повторе
  имел более высокий p95 в одиночном чтении, чем в смешанном сценарии.
- **Накладные расходы измерения малы относительно запросов.** Пустой замер
  занял 20 нс по медиане, пустой цикл с записью результата — в среднем
  108 нс на операцию. Это выше ориентира 4–5 нс из методички. Даже 108 нс
  составляют около 0,13% от самого короткого замера с БД, который занял
  81,6 мкс. Максимальная наблюдаемая задержка составила 39,7 мс.

Выводы относятся к выбранным операциям на каталоге из 10 000 записей,
одному ядру и трём повторам этого прогона.
