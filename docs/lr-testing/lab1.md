# Лабораторная №1: тесты AdminService и CabinetService

Для подготовки к защите начните с [подробной памятки](guide-to-lab1.md). Исходная формулировка задания — [PDF](../../../testing_docs/labs/ТИОПО,%20ЛР%20№1.pdf).

## Объект и границы проверки

В наборе **11 верхнеуровневых тестов**: шесть классических и пять лондонских. Каждый сервис проверяется в обоих стилях.

| Сервис | Классические | Лондонские |
|---|---:|---:|
| `AdminService` | 4 | 1 |
| `CabinetService` | 2 | 4 |

Классические тесты вызывают настоящий сервис и настоящий PostgreSQL-репозиторий, которому через `*sqlx.DB` передана отдельная SQLite `:memory:` на каждый тест. SQL исполняется SQLite, а результат проверяется через DTO/ошибку и повторное чтение репозиторием. В отчёте это часть набора unit-тестов лабораторной; при этом проверяется взаимодействие сервиса с локальным репозиторием, а не настоящий PostgreSQL. Лондонские тесты вызывают настоящий сервис с `testify/mock`-репозиторием и проверяют существенные ответы и взаимодействия. Внешние PostgreSQL, Redis и Docker тестам не нужны.

Кабинетный классический сценарий выбран для `UpdateQty`: его SQL совместим с SQLite. `AddItem` ищет запись через PostgreSQL `::date`, а `ListItems` вычисляет срок годности через `::interval`; SQLite не исполняет эти запросы без изменения production-кода. Эти методы оставлены в лондонской группе, **их настоящий SQL текущие тесты не проверяют**.

## Сценарии

| № | Стиль | Сервис и метод | Выбор данных и ожидаемый результат |
|---:|---|---|---|
| 1 | Classic | `AdminService.AddMedicine` | Составное новое лекарство с веществом, дозировкой, показанием и противопоказанием; DTO и повторное чтение подтверждают сохранение всех связей |
| 2 | Classic | `AdminService.UpdateMedicine` | Частичное изменение срока, способа применения и явных `false`; непереданные имя, состав и дозировка остаются прежними |
| 3 | Classic | `AdminService.UpdateComposition` | Вещество A заменяется на B; дозировка и показания не меняются |
| 4 | Classic | `AdminService.RemoveMedicine` | Лекарство со связями удаляется; последующий `FindByID` возвращает `ErrMedicineNotFound` |
| 5 | Classic | `CabinetService.UpdateQty` | У существующей позиции количество меняется `5 → 3` в DTO и в SQLite |
| 6 | Classic | `CabinetService.UpdateQty` | Отсутствующий ID возвращает `ErrCabinetItemNotFound`; две сохранённые позиции остаются неизменными |
| 7 | London | `AdminService.UpdateMedicine` | Внедрённая ошибка `FindByID` возвращается наружу, `Update` не вызывается |
| 8 | London | `CabinetService.AddItem` | Позиция отсутствует; `Save` получает корректный объект и вызывается один раз, `Update` не вызывается |
| 9 | London | `CabinetService.AddItem` | Ошибка поиска прерывает операцию без `Save` и `Update` |
| 10 | London | `CabinetService.RemoveItem` | Внедрённая ошибка `Delete` передаётся вызывающему коду |
| 11 | London | `CabinetService.ListItems` | Внедрённая ошибка чтения списка передаётся вызывающему коду без DTO |

В каждом тесте есть шаги Arrange, Act, Assert; в Act один вызов публичного метода сервиса. Стиль тестирования отличается от техники выбора данных: используются переход состояния, частичное обновление, классы эквивалентности, замена связей и внедрение ошибки. Это **не** полноценное попарное тестирование.

## Подготовка данных

`src/internal/test_util` содержит:

- `ids.go`: именованные детерминированные UUID;
- `builders.go`: `MedicineBuilder` и `CabinetItemBuilder` с цепочкой `With...` и `Build()`, который возвращает готовый доменный объект;
- `mother.go`: Object Mother с тремя типовыми Builder, из которых тесты сами вызывают `Build()`, — двумя вариантами лекарства и позицией аптечки с количеством 5;
- `sqlite_queries.go`: минимальные SQLite-схемы; `sqlite_repositories.go`: функции создания настоящих репозиториев и сохранения групп объектов; `cabinet_group_fixture.go`: связанная группа билдеров и отсутствующий ID для отрицательного сценария;
- `mocks/medicine_repository.go` и `mocks/cabinet_repository.go`: test doubles для лондонского стиля.

Builder позволяет явно менять только необходимые поля лекарства или позиции аптечки. Object Mother выдаёт Builder, а тест явно вызывает `Build()`. SQLite-хелпер создаёт и закрывает БД через `t.Cleanup`, наружу отдаёт только репозиторий; групповая fixture задаёт два билдера и отсутствующий ID, а `SeedMedicines`/`SeedCabinetItems` сохраняют готовые группы объектов через репозиторий и готовят состояние, а не выполняют проверяемый метод сервиса. Драйвер `go-sqlite3` использует CGO и требует C-компилятор. В каждом in-memory SQLite-пуле разрешено одно соединение: разные соединения `:memory:` иначе могли бы видеть разные базы.

## Команды и отчёты

Из `dev/`:

```bash
make test-classic       # 6 TestClassic_*
make test-london        # 5 TestLondon_*
make test               # 11 тестов ЛР №1, Allure HTML и Go coverage
make test-offline       # тот же набор с GOPROXY=off
make coverage-branch    # gocove: ветвления и условия в консоли
make allure-report      # проверить наличие отчёта после make test
make allure-open        # открыть Allure без данных покрытия
make test-clean         # убрать тестовые артефакты
```

`make test` запускает unit-, integration- и E2E-тесты и создаёт отчёт Allure 2.46.1 в `allure-report/`. Для трендов `Makefile` перед генерацией копирует сохранённую папку `allure-history-v2/` в `allure-results/history`, затем сохраняет новую папку `allure-report/history`. Содержимое истории и графики создаёт Allure; без этого переноса Allure 2 показывает только текущий прогон. Блок «Окружение» получает фактические версию Go, ОС и архитектуру из `go env`, блок «Система выполнения тестов» — сведения о запуске через `go test`. Метки `epic/feature/story` и иерархия Suites заданы в тестах через официальный адаптер Allure Go. Длительности отдельных тестов и Timeline рассчитывают адаптер и Allure с точностью до миллисекунды; отдельного замера через `time.Since` нет. Стандартный тренд длительности Allure 2 включает паузы между тестами, поэтому `scripts/fix-allure-duration-trend.mjs` заменяет в тренде длительность прогона суммой сохранённых Allure длительностей отдельных тестов. `make test-clean` удаляет результаты и отчёт, сохраняя папку истории. Между CI-запусками история передаётся артефактом. Покрытие выводится в консоли и сохраняется отдельно в `coverage.out`.

Фактический прогон на 2026-10-16 (Go coverage; `gocove` — прежний расчёт):

| Метрика | Значение | Область |
|---|---:|---|
| Statements | 29,2% | все `service` и все PostgreSQL-репозитории |
| Инструментированные строки | 400/1453 = 27,5% | та же область |
| Blocks | 14,8% | только `service`, `gocove` |
| Branches | 10,0% | только `service`, `gocove` |
| Conditions | 2,7% | только `service`, `gocove` |

Знаменатели Go и `gocove` различаются: сравнивать эти проценты как одну метрику нельзя. Пользователь прямо отдал приоритет распределению сценариев по методам, а не максимальному покрытию. Низкие общие проценты не скрываются исключением production-кода.

## SonarQube и процессы

`sonar-project.properties` импортирует готовый `coverage.out`; SonarQube не запускает Go-тесты и не генерирует профиль самостоятельно. Команды без Docker: `make sonar-up`, `make sonar-status`, `SONAR_TOKEN=... make sonar-scan`, `make sonar-down`. Для них нужна локальная ZIP-установка SonarQube и `sonar-scanner` в `PATH`. Факт успешного анализа в локальном SonarQube **ещё не подтверждён**.

`make test` передаёт Go один пакет `src/internal/service`, поэтому 11 тестов ЛР №1 исполняются в одном тестовом бинарнике. `-shuffle=on` меняет порядок тестов, а `-count=1` отключает кэш результата. `GOPROXY=off` запрещает загрузку модулей из интернета во время offline-прогона при условии, что зависимости уже есть локально.

## Что не следует заявлять на защите

- Не говорить, что SQLite-тесты доказывают совместимость со всем PostgreSQL-диалектом или production-миграциями. Проверяются только исполненные здесь SQL-пути.
- Не говорить, что весь репозиторий лекарства или аптечки покрыт: часть их публичных методов и ошибочных SQL-ветвей не тестируется.
- Не говорить, что все требования PDF выполнены буквально: нынешние сценарии не дают пару «позитивный + негативный» **для каждого** публичного метода `AdminService`; у `CabinetService` тоже не все методы имеют обе пары. Требование Data Builder теперь выполнено, но полного покрытия публичного API нет.
- Не говорить, что `pgxmock`, `redismock` или `miniredis` используются сейчас: их в текущих тестах нет. Если устное требование преподавателя об этих библиотеках обязательно, нужна отдельная доработка.
